## 1. 基线与要解决的问题

最近 10 个运维相关 issue 是 #417、#312、#311、#310、#212、#211、#166、#143、#89、#78，不能等同为 10 次每日事故。
至少五个交易日留下日链路故障记录，但缺少全量运行分母，暂不声明历史故障率。
9/21 三端恢复证据成立；#423 节点部署和 #311 的 9/16 历史恢复仍缺独立回执。

供应商空响应、断连、延迟是触发条件；可直接改进的是：
修复未及时部署、重试重复全量请求、子进程超时后残留、契约组合晚失败，以及事故提前关闭。
不把服务端限流作为已证实的唯一根因。

既有本地回归：日链路 134 passed / 2 failed（GNU/BSD sed 环境差异）；
全量 2,688 passed / 90 failed / 7 skipped，含平台差异及既有 planning 缺口。
GitHub CI 因账单/额度未启动，不能作为通过证据。

## 2. 目标与不可退让的验收条件

目标是让每日任务在有界成本内成功，失败时安全终止、保存证据、按缺口恢复；
让“合并代码、部署节点、修复日期、发出通知”分别可确认。

- 数据可信度：缺失/冲突数据仍 fail-closed；不得以空表、伪造日期、放宽覆盖率换绿灯。
- 进程隔离：受控进程组在超时/失败退出前完成回收；无法确认回收时禁止自动重试。
- 恢复效率：已核验的成功项不无条件重抓；复用必须验证完整语义身份并进入新 attempt。
- 发布闭环：每个采集节点、批准版本、unit 和受影响日期都有机器可读回执。
- 观测闭环：数据结果、通知结果、SLA 结果独立；迟到成功不能重标为按时成功。
- 关闭条件：工程、Linux 回归、逐节点部署、历史缺口和观察期分别通过；PR 合并不自动关闭总任务。

连续 10 个交易日为首轮观察窗口，从最终批准版本在两个采集节点验收之后开始。
目标：节点×交易日缺口为 0、自动有界恢复后的完整成功率 100%、遗留写入/重试重叠为 0、
超预算且未告警为 0、部署漂移为 0。首轮成功率以 >=95% 为候选目标：
先取得完整分母，再在实施前冻结运行指标版本；不得回写或剔除失败样本。
通知可达性单独报告，不反向证明数据成功。该观察窗口尚未执行，未创建定时监控。

## 3. 选定路线与替代方案

采用“小批次修复 + 精确故障回归 + GitHub 发布 + 节点回执”，不重建调度平台。

| 路线 | 取舍 |
| --- | --- |
| 只延长所有 timeout | 拒绝。不能消除重复请求、失效截止时间、孤儿进程和部署漂移。 |
| 只增加重试次数 | 拒绝。先建立统一截止时间、残余集合和终态证据，再评估次数。 |
| 引入跨节点缓存/中心采集 | 暂不采纳。会改变独立采集边界，当前尚无成本及故障隔离证据。 |
| 同 Job 共享分钟来源 | 暂不实施。现行设计要求正式 5m 直接采集，现有 Eastmoney 聚合实现与文档需先解决一致性。 |
| 降低覆盖/READY 门槛 | 禁止。完整性门禁在既有事故中有效。 |
| 大规模替换 systemd/编排框架 | 暂不需要。先修现有明确可复现的生命周期缺陷。 |

## 5. 技术设计边界

### 进程与重试

正常作业在独立 POSIX session/process group 中启动，launcher 不得后台脱离该组。
超时后向整个受控组发 TERM，给有限清理窗口；仍存活则 KILL，
确认组不再存在之后才释放控制、进入后续作业或重试。
无法确认回收输出专门错误，外层 wrapper 不自动重试。
不会对宿主默认进程组、同用户全部进程或未知 PID 批量发送信号。

进程组不等于整个系统的后代树：主动 setsid 脱离的外部 collector 和控制器 SIGKILL
仍需要生产 systemd cgroup 兜底。上线前核验 KillMode/SendSIGKILL，
并做真实服务终止测试；不能以 macOS 本地用例替代这个门禁。
新回收等待是独立、有界的安全退出预算，不延长供应商采集权限或数据 SLA。

### 恢复身份与材料生命周期

恢复身份包含 node/date/universe、频率、provider、数据配置/policy、schema、code revision
及每个物理文件的校验和。缺失/不兼容时拒绝复用；
成功种子复制到新 attempt，原始成功/失败证据均不可改写。
checkpoint 是恢复材料，不是 READY，也不因 status=done 而跳过日期和无交易证据验证。
TMP、跨 Job cache、正式发布物采用各自保留政策，不把方便重试的缓存提升为正式数据产品。

### 兼容性与能力

选择四条 READY 时必须考虑整组 schedule/config 兼容性；
不能先逐 lane 标记完成，再在 DWD 前发现组合不可用。
运行参数与语义契约的划分需显式评审，不删除现有 config hash 检查。

## 6. 技术评审机制与首轮结论

本轮采用同一执行助手的“方案阶段 / 反向技术审查阶段 / 测试验收阶段”分离，
不是独立人类或独立模型审批。未擅自向其他人员发消息或申请其评审。
评审记录保留阻断项、整改及证据；每批代码仍需 diff 复审和失败场景验证。

首轮结论：PASS_SCOPED_IMPLEMENTATION / NO_GO_PRODUCTION。
B 的有界工程实现可启动；A/C/D/E/F 按依赖推进。生产放行尚不具备条件。

| 评审问题 | 结论 / 决议 |
| --- | --- |
| 会不会削弱数据完整性？ | 方案禁止变更门禁；第一批仅进程控制。 |
| 杀掉直接父进程能否证明结束？ | 不能。需覆盖 shell 管道、父进程先退与 TERM 无响应；不能仅用 Popen.wait 作为全组完成证据。 |
| 进程回收无法确认时可否继续？ | 不可；必须可见失败并阻止自动重试。 |
| 复用能否仅按日期或文件名？ | 不可；完整身份和 checksum 是前置条件。 |
| 1m/5m 共享是否天然等价？ | 否。发现既有文档与 fallback 实现差异，单独治理，不借优化放行。 |
| CI 红灯能否当环境问题忽略？ | 不可。逐项归类；Linux 未运行就是缺证据。 |
| OCI 在线能否用作其他节点的替代管理入口？ | 不可。当前镜像角色不恢复旧控制入口，也不替代目标节点 NexusAgent 连接。 |
| PR 合并可否关闭事故和总方案？ | 不可。关闭依赖节点、日期、通知/部署和观察期证据。 |

## 7. 发布、回滚与停止条件

1. 小 PR：记录工作包、重现测试、基线对比和 docs-impact；不使用 Closes 提前关父任务。
2. 关键套件及 make check；测试未执行、失败与通过分别记录。
3. 只有允许的 NexusAgent 节点可做正式部署；从 GitHub 获取批准 revision。
4. 停 timer → 确认无运行 lane → 保存版本/unit/指针证据 → 干净 fast-forward
   → 安装同版本 unit → preflight → timer停止时 reset-failed → 恢复 timer并记下次触发。
5. 先在一个采集节点验证手动 shadow/fault 场景，再部署另一节点；保留两个独立采集结果。
6. 回滚只恢复代码/unit/运行设置到记录版本，不能重写不可变数据、倒退 CURRENT 日期或删除失败证据。
7. 出现 late write、跨日期复用、契约放宽、错误包发布、未知存活进程或无法验证回滚时停止放行。

GitHub runner 未启动；正式 Linux 基线及历史回执不全。
不通过 SSH、旧 OCI 控制入口或 ad-hoc 文件分发绕过管理边界。无需阻塞本地方案与测试驱动改造。

OCI 范围已澄清（2026-09-22）：用户确认当前为 Base V2.1 + Daily，OCI 接收 CN01 的
